# Checkout extensions migration — developer handoff

**Branch:** `migration/polaris-web-components` (off `master`, nothing merged or deployed yet)
**App:** `cellexia-aov-ltv-booster`, client_id `2aadc2719a5bc649804cb42c0cbb917c` — this IS the production app (same app installed on the live store, not a separate sandbox app)
**Status:** code-complete, typechecked, builds successfully. **No runtime/browser verification has happened yet.** That's the main thing this doc asks you to do before this ships.

## Why this exists

Shopify requires checkout UI extensions to migrate off the React-based architecture (`@shopify/ui-extensions-react`) to Polaris Web Components (`@shopify/ui-extensions` + Preact), API version `2025-10`+. Shopify's own deploy-blocking deadline for this was **2026-10-01**, which has already passed as of this handoff. All four checkout extensions in this app have been migrated to `api_version = "2026-04"`.

### The actual mechanical migration, same across all four
- `react` / `react-reconciler` / `@shopify/ui-extensions-react` → `preact` / `@preact/signals` / `@shopify/ui-extensions@2026.4.x`
- `tsconfig.json`: added `"jsxImportSource": "preact"` and `"shopify.d.ts"` to `include` (that file is auto-generated by `shopify app build`/`dev` — don't hand-edit it, and regenerate it with a build if you add/rename source files)
- Every React hook (`useApi`, `useAppMetafields`, `useCartLines`, `useShippingAddress`, `useLocalizationMarket`, `useLanguage`, `useAttributeValues`, `useTranslate`, `useApplyCartLinesChange`, `useApplyDiscountCodeChange`, `useDiscountCodes`, `useInstructions`, `useLocalizationCountry`, `useStorage`, `useSettings`) replaced by reading directly off the global `shopify` object (e.g. `shopify.lines.value`, `shopify.appMetafields.value`, `shopify.applyCartLinesChange(...)`) — verified against the actual installed `@shopify/ui-extensions` package types in `node_modules`, not just doc summaries
- JSX components renamed to lowercase Polaris Web Components: `BlockStack`/`InlineLayout`/`InlineStack` → `<s-stack>`, `Text` → `<s-text>`, `Icon` → `<s-icon>`, `Link` → `<s-link>`, `View` → `<s-box>`, `Pressable` → `<s-clickable>`, `Badge` → `<s-badge>`, `Checkbox` → `<s-checkbox>`, `Heading` → `<s-heading>`, `Image` → `<s-image>`, `Button` → `<s-button>`, `SkeletonText` → `<s-skeleton-paragraph>`
- Multi-target extensions (`checkout-trust`, `checkout-delivery`, `checkout-upsell`) split one `Checkout.tsx` into two small entry files (`BlockRender.tsx` + the second target's file) both rendering a shared `Extension.tsx` — the new architecture has no documented way for one file to register two checkout placements, so each `[[extensions.targeting]]` entry now points at its own file, matching the toml's own documented one-module-per-target pattern

## Known visual deltas (flagged to the merchant, not yet confirmed by eye)

Three icon sources have no exact equivalent in the new reduced icon set:
- `success` → `check-circle`
- `orderBox` → `order`
- `checkmark` → `check`

Text styling: old `size="small" emphasis="bold"` can't be expressed in one `<s-text>` (the `type` attribute is a single enum) — resolved as `type="strong"` for titles, `color="subdued"` for body text. Also: `s-text`'s `tone` list has no `"accent"` value at all (verified from the installed types) — anywhere the old code used `appearance="accent"` on text, it now renders with no tone override (just `type="strong"` carrying the emphasis). Same for `s-icon`'s `tone="accent"` → mapped to `"auto"`.

`checkout-upsell`'s product rows lost the old `columns={[60, 'fill', 'auto']}` fixed/fill/auto grid sizing — `s-stack` has no per-item column-width control, so rows now lay out via plain flex. May look different (thumbnail/button proportions), not a logic change.

## What actually needs verification before deploy — the important part

Nothing here has run in a real browser yet. Static typechecking (`tsc --noEmit`, clean on all four) and `shopify app build` (succeeds on all four) prove the code *compiles and bundles* — they prove nothing about runtime behavior. Two specific categories of risk, concentrated in the two cart-mutating extensions:

### 1. Event-handling timing (`checkout-protection`)
The checkbox's `onChange` signature changed from `(value: boolean) => void` to `(event: Event) => void`, now read via `(event.currentTarget as unknown as {checked: boolean}).checked` — see `extensions/checkout-protection/src/Extension.tsx`, the `<s-checkbox onChange={...}>` handler near the bottom of `ProtectionCard`. This is type-correct but unverified against the real custom element's event timing. **Test:** toggle the checkbox on and off repeatedly in a real checkout, confirm the cart line is added/removed correctly every time, including rapid double-clicks.

### 2. Signal-reactivity vs React effect timing (`checkout-protection`'s `RewardsSafetyNet`, `checkout-upsell`'s recommendation fetch)
Both extensions have `useEffect` blocks that depend on `shopify.lines.value` / `shopify.discountCodes.value` changing to re-fire mutation logic (gift-line removal, discount-code attach/yield, recommendation refetch). Preact's signal-based reactivity doesn't necessarily trigger re-renders at the same granularity React's hook-based `useCartLines()` did. **Test specifically:**
- Add a gift-tier-qualifying cart, confirm the KIT discount code attaches exactly once (not duplicated, not missing)
- Remove a cart line that drops below a gift tier, confirm the gift line gets removed once (not left behind, not removed twice causing an error)
- In `checkout-upsell`, rapid-tap "Add" on an offer, confirm it doesn't add the product twice

### 3. `shopify.storage` persistence semantics
The "only auto-add protection once," "only remove gift line once," "only attach KIT code once" guards all read/write `shopify.storage` (see `PROTECTION_STATE_KEY`, `KIT_ATTACHED_KEY`, `KIT_YIELDED_KEY`, `GIFT_REMOVED_PREFIX` constants). Type-identical to the old `useStorage()` hook, unverified at runtime. **Test:** reload the checkout page mid-session after an auto-add or code-attach fires, confirm it doesn't repeat.

### 4. GraphQL query behavior
`shopify.query(...)` replaces `useApi().query(...)` with the same signature — verify the Storefront API calls in `checkout-protection` (variant price fetch) and `checkout-upsell` (manual variant fetch + `productRecommendations`) actually return data in a live checkout, including the `@inContext(country:)` localization.
