# Checkout extensions migration — please merge into your own template

**Why you're getting this:** we had to migrate `checkout-trust`, `checkout-delivery`, `checkout-protection`, and `checkout-upsell` to Shopify's new Polaris Web Components architecture ourselves, ahead of your last two update packages (v35, v36), because Shopify set a hard deploy-blocking deadline (2026-10-01) for the old React-based architecture and we couldn't wait for it to land in your release cycle. It's done and already deployed (Shopify app version `cellexia-aov-ltv-booster-73`).

**The problem:** your update packages don't know this happened — v35 and v36 both still shipped the old pre-migration React code for all four extensions. We've had to manually re-apply our migrated versions on top of your updates both times, which is extra work on our end and a real risk of us missing something in a future merge. **Please pull this migration into your own source tree** so your next package already ships the correct architecture, and we stop having to do this by hand every release.

This package includes the four migrated extension folders (source only — `node_modules`, `dist/`, and the auto-generated `shopify.d.ts` are excluded; your own build will regenerate those) plus this guide explaining exactly what changed and why, so you can either drop these files in directly or re-derive the same changes against your own latest versions of these files if they've diverged since.

## What changed, mechanically, in every one of the four extensions

1. **`shopify.extension.toml`**: `api_version` bumped from `2025-07` to `2026-04`. **Handle and `uid` are unchanged** — do not regenerate these, they're what keeps Shopify treating this as the same extension rather than a new one.
2. **`package.json`**: removed `react`, `react-reconciler`, `@shopify/ui-extensions-react`. Added `@shopify/ui-extensions: "2026.4.x"`, `preact: "^10.10.x"`, `@preact/signals: "^2.3.x"`.
3. **`tsconfig.json`**: added `"jsxImportSource": "preact"` under `compilerOptions`, and added `"shopify.d.ts"` to `include`. That file is auto-generated by `shopify app build`/`shopify app dev` — don't hand-write it, and regenerate it (just run a build) if you add or rename source files.
4. **File structure**: any extension that previously registered two targets from one `Checkout.tsx` (via two `reactExtension(...)` calls) is now split into two small entry files — e.g. `BlockRender.tsx` and `ActionsRenderBefore.tsx` (or `ShippingOptionListRenderAfter.tsx` for `checkout-delivery`) — both importing and rendering a shared `Extension.tsx`. This is because the new architecture has no documented way for one module to export render functions for two different targets; each `[[extensions.targeting]]` entry needs its own module. Update the `module = "..."` paths in the toml to match (see the included tomls for the exact mapping).
5. **The actual component/rendering code** (what used to be `Checkout.tsx`, now `Extension.tsx`): rewritten from React + `@shopify/ui-extensions-react` hooks/JSX to Preact + the `shopify` global object + `<s-*>` Polaris Web Components. See the full mapping table below — **everything here was verified against the actual installed `@shopify/ui-extensions` package types, not guessed from documentation**, so please treat these as correct, not as a starting point to re-derive from scratch.
6. **Pure business logic is completely untouched.** `trust-logic.ts` and `delivery-engine.ts` have zero framework dependency and were not modified at all — same file, same content, just copied over as-is.

## API mapping (hooks → global object)

| Old (React hook) | New (`shopify` global) |
|---|---|
| `useApi()` | removed — destructure what you need directly off `shopify` |
| `useAppMetafields()` | `shopify.appMetafields.value` |
| `useCartLines()` | `shopify.lines.value` |
| `useShippingAddress()` | `shopify.shippingAddress?.value` (note: the property itself is optional, not just the value) |
| `useLocalizationMarket()` | `shopify.localization.market.value` |
| `useLanguage()` | `shopify.localization.language.value` |
| `useLocalizationCountry()` | `shopify.localization.country.value` |
| `useAttributeValues(keys)` | read `shopify.attributes.value` (an array) and find by `.key` yourself — no direct multi-key equivalent |
| `useTranslate()` | `shopify.i18n.translate` |
| `i18n.formatNumber`/`formatCurrency` (from `useApi()`) | `shopify.i18n.formatNumber` / `shopify.i18n.formatCurrency` |
| `useApplyCartLinesChange()` | `shopify.applyCartLinesChange(...)` — called directly, not via a hook |
| `useApplyDiscountCodeChange()` | `shopify.applyDiscountCodeChange(...)` — called directly. Also: drop the old `'applyDiscountCodeChange' in api ? ... : undefined` defensive guard — it's unconditionally present on `CheckoutApi` for `purchase.checkout.block.render`, confirmed from the type declarations. |
| `useDiscountCodes()` | `shopify.discountCodes.value` |
| `useInstructions()` | `shopify.instructions.value` |
| `useStorage()` | `shopify.storage` (same `read`/`write` methods, same async contract) |
| `useSettings()` | `shopify.settings.value` |
| `extension.editor` (from `useApi()`) | `shopify.extension.editor` |
| `shopify.query(...)` (Storefront/Admin GraphQL) | unchanged — still `shopify.query<Data>(graphql, { variables })`, same signature |

## Component mapping

| Old (`@shopify/ui-extensions-react/checkout`) | New (`<s-*>` web component) | Notes |
|---|---|---|
| `BlockStack` | `<s-stack direction="block">` | |
| `InlineStack`, `InlineLayout` | `<s-stack direction="inline">` | **No per-item column-width control** (the old `columns={[60, 'fill', 'auto']}` has no equivalent on `s-stack`) — use `<s-grid gridTemplateColumns="60px 1fr auto">` instead if you need fixed/fill/auto column sizing (verified: `s-grid` supports `gridTemplateColumns` as a plain CSS grid-template string). |
| `Text` | `<s-text>` | `size="small"` → `type="small"`; `emphasis="bold"` → `type="strong"` (these are mutually exclusive on the new component — you can't have both at once, pick whichever matters more for your UI); `appearance="subdued"` → `color="subdued"` (not `tone`); `appearance="success"`/`"critical"` → `tone="success"`/`"critical"` (direct match); **`appearance="accent"` has no `tone="accent"` equivalent on `s-text`** — verified against the type declaration, the tone list is only `auto/neutral/info/success/warning/critical/custom`. |
| `Icon` | `<s-icon>` | `source` → `type`; `appearance` → `tone`. **The icon set is reduced** — several old `source` values have no exact match: `success`→`check-circle`, `orderBox`→`order`, `checkmark`→`check` (these render a visibly different glyph, not just a rename — worth a design look). Exact renames with no visual change: `starFill`/`starHalf`/`star` → `star-filled`/`star-half`/`star`. `appearance="accent"` → `tone="auto"` (no accent tone on `s-icon` either). |
| `Badge` | `<s-badge>` | `tone` list is only `auto/neutral/critical` (no success/accent) |
| `Checkbox` | `<s-checkbox>` | **Real behavior change, not just renaming**: `onChange` used to be `(value: boolean) => void`; it's now `(event: Event) => void` — read the new checked state via `(event.currentTarget as unknown as {checked: boolean}).checked`. Label: children work the same way (an `<s-text>` child), `s-checkbox`'s label slot explicitly supports only `s-text`/`s-link` children. |
| `View` | `<s-box>` | `cornerRadius` → `borderRadius` |
| `Pressable` | `<s-clickable>` | `onPress` → `onClick` |
| `Button` | `<s-button>` | `kind` → `variant`; `onPress` → `onClick` (event-based now, but harmless if your handler takes no args) |
| `Heading` | `<s-heading>` | No `level` prop exists — drop it, no behavioral impact for a single heading |
| `Image` | `<s-image>` | `source` → `src`; `accessibilityDescription` → `alt`; `fit` → `objectFit`; `cornerRadius` → `borderRadius`; `aspectRatio` takes a **string** (`"1"`), not a number |
| `SkeletonText` | `<s-skeleton-paragraph>` | No `inlineSize` prop — only an optional `content` string to size itself off |
| `SkeletonImage` | **no equivalent exists** | We fell back to a plain bordered `<s-box>` placeholder — same pattern already used for "no image available" elsewhere in these files |
| `Link` | `<s-link>` | `to` → `href`; `external` → `target="_blank"` |

Other things we found no equivalent for:
- `alignItems`/`blockAlignment` on stacks: no `"baseline"` value on `s-stack`'s `alignItems` — we used `"center"` instead.
- `<s-icon>`'s type list is a **fixed, reduced enum** — check `type` against the actual installed package before adding any new icon usage; don't assume an old `source` name will still work.

## What we have NOT done, and you may want to

- **The 3 icon substitutions and the text-style tradeoff above are judgment calls**, not design decisions — they haven't been confirmed as acceptable by whoever owns the storefront's visual design. If you have better icon choices or a cleaner way to express the old `size="small" emphasis="bold"` combo, we're not precious about ours.
- **We used `s-grid` for `checkout-upsell`'s product rows** to preserve the old fixed/fill/auto column layout — if you have a different preferred approach to that layout, this is the one place we deviated from a pure 1:1 port.
- **Live runtime testing has been limited** — these extensions typecheck clean and build successfully, and the logic underneath is provably unchanged, but we have not been able to fully click through every scenario (cart mutations, discount code interactions) in a live checkout. Worth your own QA pass if you have better test-store access than we did.

## Two unrelated but recurring bugs in your update packages, while we're at it

1. `scripts/prisma-env.mjs` and `validation/harness.mjs` both need `shell: process.platform === "win32"` added to their `execFileSync(...)` options for Windows compatibility — this keeps shipping without it (confirmed missing again in both v35 and v36) despite being documented as fixed back in the v22 round.
2. `shopify.app.toml.example`'s scopes boilerplate still suggests `read_price_lists,write_price_lists` — this app doesn't use either, we use `write_markets` instead. Worth removing from the template.

Happy to answer anything about the mapping choices above — we verified every single one against the actual installed `@shopify/ui-extensions` package types before using it, not from docs alone, so if something looks surprising it's probably because the architecture genuinely changed that way, not a guess on our part.
